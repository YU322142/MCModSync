# MCModSync 中文使用指南

> [!WARNING]
> 本项目包含 AI 辅助生成或修改的代码。使用前请自行审阅、在测试实例验证，并为客户端保留可恢复备份。请勿把不可信或无权分发的文件放进同步目录。

本文是 README 的补充，面向自行运营 Minecraft 客户端整合包的服主。

## 一、工作方式

MCModSync 在游戏加载前读取 `modsync.properties`，下载你的 Mod、资源包和服务器列表清单；随后按清单下载文件、校验 MD5，并保存同步历史。默认安全策略是：任何必需清单不可用或文件校验失败时，阻止客户端继续启动。

它不会自动提供文件托管、账号鉴权或 CDN 服务；这些均由部署者自行选择并维护。

## 二、发布目录与托管布局

推荐为每个客户端版本准备独立目录，避免不同 Minecraft/Fabric 版本混用：

```text
release/
└─ 1.21.11-fabric/
   ├─ mods.txt
   ├─ mod-a-1.0.0.jar
   ├─ mod-b-2.0.0.jar
   ├─ resourcepacks.txt       # 可选
   ├─ pack.zip                # 可选
   ├─ serverlist.txt          # 可选
   └─ servers.dat             # 可选
```

对应配置：

```properties
manifest=https://files.example.com/release/1.21.11-fabric/mods.txt
resourcePackManifest=https://files.example.com/release/1.21.11-fabric/resourcepacks.txt
serverListManifest=https://files.example.com/release/1.21.11-fabric/serverlist.txt
```

文件名改动会被视为新文件。发布更新时应先在本地完成 Mod 测试，再生成清单，最后将 JAR/ZIP/`servers.dat` 与清单作为一组上传。不要先上传新清单再晚些上传文件，否则玩家可能在中间状态启动失败。

## 三、生成与检查清单

### Mod 清单

```powershell
java -jar MCModSync-1.6.10.jar "D:\Release\1.21.11-fabric\mods" "D:\Release\1.21.11-fabric\mods.txt"
```

生成器会读取每个 JAR 的 `fabric.mod.json`，记录 Mod ID、文件名与 MD5，并拒绝空目录或重复 Fabric Mod ID。请将清单生成器 JAR 放在发布 `mods` 目录之外运行，避免把它意外纳入要分发的 Mod 清单。

### 资源包清单

当前命令一次为一个 ZIP 生成清单：

```powershell
java -jar MCModSync-1.6.10.jar --resourcepack "D:\Release\1.21.11-fabric\pack.zip" "D:\Release\1.21.11-fabric\resourcepacks.txt"
```

将 `pack.zip` 和 `resourcepacks.txt` 上传到同一目录。若不使用资源包同步，在客户端配置中设 `syncResourcePacks=false`。

### 服务器列表清单

```powershell
java -jar MCModSync-1.6.10.jar --serverlist "D:\Release\1.21.11-fabric\servers.dat" "D:\Release\1.21.11-fabric\serverlist.txt"
```

将两个文件一同上传；不使用此功能时设 `syncServerList=false`。服务器列表包含你设定的服务器信息，应仅写入允许向玩家公开的地址与名称。

## 四、玩家端安装和升级

1. 确认玩家安装的 Minecraft、Fabric Loader、Java 与发布端要求一致。
2. 将 MCModSync JAR 放入实例根目录下的 `mods` 文件夹。
3. 将 `modsync.properties.example` 复制到实例根目录并改名为 `modsync.properties`。
4. 填写真实清单 URL；首次启动前备份 `mods`、`resourcepacks` 与 `servers.dat`。
5. 首次启动完成下载和校验后，按提示重启游戏。

默认会保留玩家自行添加的内容，但服主应在真实玩家群体发布前先用全新实例、已有旧版本实例、手机启动器实例各测试一次。

## 五、更新操作清单

每次整合包升级按此顺序操作：

1. 复制旧发布目录，绝不在唯一副本上直接修改。
2. 在测试客户端增删 Mod，并成功进入世界。
3. 更新资源包或 `servers.dat`（如有）。
4. 重新生成各个受影响的清单。
5. 上传所有实际文件和清单；确认每个 URL 能直接下载。
6. 用干净客户端测试首次安装，再用旧客户端测试升级。
7. 观察日志与 `.modsync` 历史文件后再通知玩家。

## 六、安全与隐私建议

- 使用 HTTPS 和你能控制的域名；不要在 URL 中永久写入可泄露的访问令牌。
- 若必须使用签名 URL，请控制有效期，并不要把包含该 URL 的 `modsync.properties` 提交到仓库。
- 对上传的 JAR/ZIP 做恶意软件扫描，并保留源文件、生成的清单及发布时间记录。
- 限制发布目录写入权限；被篡改的清单会让所有客户端获取攻击者指定的文件。
- 变更前备份；不要在生产玩家实例上首次试用新版本。

## 七、诊断位置

发生问题时，收集 Minecraft `logs/latest.log`、游戏根目录下 `.modsync` 中的状态/历史信息，以及实际打开的清单 URL。隐去账号、令牌和内部域名后再将日志发给他人协助分析。
