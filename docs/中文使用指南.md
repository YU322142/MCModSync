# MCModSync 1.8.2 中文使用指南

> [!WARNING]
> 本项目包含 AI 辅助生成或修改的代码。使用前必须自行审阅，在隔离实例验证，并保留能恢复的完整备份。不要发布不可信或无权分发的 JAR。

本文补充 README，重点说明长期维护一套“必须模组 + 推荐模组”客户端的发布流程。

## 1. 工作模型

每份 v4 `mods.txt` 同时承担文件完整性清单和推荐目录的职责：

- `required` 条目始终进入目标组合；
- `recommended` 条目由平台规则和客户端保存的选择共同决定；
- 每个条目包含 MD5 与 SHA256；
- 每个条目分别包含中文描述和英文描述；
- `catalog-version` 控制推荐选择何时重新计算；
- 不兼容平台是排除列表，支持 `windows,mac,linux,mobile`。

客户端先读取清单和推荐选择，再计算最终目标组合。下载、校验、旧版本替换、推荐取消移出均在同一事务中执行；事务失败会尝试回滚。

### 从旧版升级到 v4

已部署 1.6.x 或 1.7 客户端时不能直接替换成 v4 清单。使用 1.8.2 图形发布器时，把 `MCModSync-1.8.2.jar` 放在被扫描的发布 `mods` 目录中；生成正式 v4 `mods.txt` 的同时，工具会生成兼容旧版的 `mods-upgrade-v2.txt`。也可以单独执行：

```powershell
java -jar MCModSync-1.8.2.jar --upgrade-v2 "D:\Release\mods" "D:\Release\mods-upgrade-v2.txt"
```

然后严格按以下顺序发布：

1. 上传 `MCModSync-1.8.2.jar` 和目录中的所有 JAR；
2. 暂时让客户端已经配置的线上 `mods.txt` URL 返回 `mods-upgrade-v2.txt` 的内容；
3. 用旧客户端启动一次，看到更新/重启提示后再启动，确认日志版本已变成 1.8.2；
4. 等仍需支持的旧客户端都完成升级后，才让同一个线上 URL 返回正式 v4 `mods.txt`；
5. 再提高或确认 `catalog-version`，检查电脑端推荐选择和手机端自动处理日志。

不要只把 `mods-upgrade-v2.txt` 上传成一个新 URL，旧客户端不会主动寻找它。v2 不支持推荐分类，过渡阶段会把全部条目视为必须；切到 v4 后，客户端会按最终推荐选择自动移出不需要的 JAR。直接让旧同步器读取 v4 会安全阻止启动，这是格式不兼容保护，不是游戏崩溃。

项目已用真实 1.6.10 JAR 和 1.7.0 JAR 对“下载当前同步器、按 `mcmodsync` Mod ID 替换旧文件、正常退出并要求重启”做过端到端验证。

## 2. 发布目录

每个 Minecraft/Fabric 组合应使用独立目录：

```text
release/
└─ 1.21.11-fabric/
   ├─ mods.txt
   ├─ fabric-api.jar
   ├─ required-mod.jar
   ├─ recommended-windows.jar
   ├─ resourcepacks.txt       # 可选
   ├─ pack.zip                # 可选
   ├─ serverlist.txt          # 可选
   └─ servers.dat             # 可选
```

不要在不同 Minecraft 版本间共用一个 `mods.txt`。当前 `MCModSync-1.8.2.jar` 应放在扫描目录内，以便同步器自身更新并生成旧版过渡清单；不参与客户端分发的其他管理工具应放在扫描目录之外。

## 3. 使用图形发布工具

运行：

```powershell
java -jar MCModSync-1.8.2.jar
```

选择测试完成的 `mods` 目录后，打开必须/推荐编辑表格：

1. 需要沿用旧设置时，先勾选“扫描后选择上次清单”；扫描当前 `mods` 后选择上次发布的 v3/v4 `mods.txt`。
2. 通过“必须 / Required”和“推荐 / Recommended”复选框选择类型。每行始终只能选中一个，勾选一侧会自动取消另一侧。
3. 保证 Fabric API、前置库和服务端要求的内容选为必须；把性能增强、地图、光影等允许用户取消的内容选为推荐。
4. 对每个推荐模组勾选其不能运行的平台。例如不支持手机端就只勾选“手机不兼容”。
5. 检查从 `fabric.mod.json` 读取的名称、版本和描述，并人工填写或校对中文描述。Fabric 元数据通常只有一个描述字段：含中文时进入中文列，否则进入英文列，不会自动翻译。选择上次清单后会保留原有双语描述。
6. 修改 `catalog-version`。建议使用发布号，如 `2026-07-29-r1`，不要重复使用旧版本号。
7. 生成清单并与所有 JAR 一起上传。若扫描目录包含当前 MCModSync JAR，发布器会同时生成正式 v4 清单和旧版升级用 v2 清单；不要把两者的使用阶段混淆。

合并时以当前扫描目录的 JAR 集合为准。相同 Mod ID 会保留旧分类、不兼容平台、显示名称和中英文描述，同时刷新文件名、版本和双哈希；新增 JAR 使用扫描默认值，已删除 JAR 不会带入新清单。

命令行模式生成的全部是必须模组，适合不需要推荐分类的自动化发布：

```powershell
java -jar MCModSync-1.8.2.jar "D:\Release\mods" "D:\Release\mods.txt"
```

## 4. 推荐清单版本策略

以下变化都应增加 `catalog-version`：

- 新增或移除推荐模组；
- 必须/推荐类型改变；
- 不兼容平台改变；
- 希望电脑端重新询问选择；
- 希望手机端对新发布批次再自动处理一次。

仅替换必须模组版本时不强制要求改变推荐清单版本，但为了审计清晰也可以同步增加。

客户端发现版本变化会在日志写入：

```text
推荐清单版本更新: old-version -> new-version
```

电脑端随后重新显示选择窗口；手机端自动选择该新版本中所有兼容推荐模组，并在本版本成功同步后标记为已经处理。

## 5. 中文与英文语言策略

客户端语言由以下优先级决定：

1. JVM 参数 `-Dmodsync.language=zh_cn` 或 `en_us`；
2. 游戏根目录 `modsync.properties` 中的 `language`；
3. `language=auto` 时读取 Minecraft `options.txt` 的 `lang`；
4. 没有可用设置时跟随操作系统语言，非中文系统默认英文。

推荐选择窗口按当前语言显示对应描述；该语言描述为空时自动回退到另一种语言。发布工具的编辑表头同时标注中文和英文，主要窗口也会按系统语言或 JVM 参数显示中文/English。

```properties
language=auto
# language=zh_cn
# language=en_us
```

## 6. 手机端“一次自动处理”

手机端自动处理状态按游戏实例和 `catalog-version` 保存：

- 首次处理本版本：下载全部兼容推荐模组；
- 同一版本以后：正确存在的推荐模组继续保留；
- 被删除或哈希错误的推荐模组不会再次自动下载；
- 日志给出下载直链、SHA256 和目标 `mods` 目录；
- 推荐模组缺失允许继续启动；
- 必须模组缺失仍自动修复，修复失败则正常退出并阻止进入游戏。

如果服主确实需要让手机端重新自动处理，发布新的 `catalog-version`。不要指导普通玩家随意删除状态文件。

## 7. 电脑端取消与恢复

用户取消已经安装的推荐模组时，文件被移动到：

```text
.modsync/backups/<时间与事务编号>/
```

需要恢复时有两种方式：

1. 等待下一次推荐清单版本更新，在选择窗口重新勾选；
2. 关闭游戏和所有 Java 进程，将备份 JAR 手动放回 `mods`，并确认它仍与当前清单哈希一致。

推荐选择保存在 `.modsync/recommended-selection.properties`。同一版本不会重复询问。

## 8. 安全发布顺序

1. 复制旧发布目录作为新版本工作副本。
2. 在隔离客户端更新 Mod，并实际进入世界测试。
3. 运行图形发布工具，分类、标记平台、更新清单版本。
4. 先上传所有 JAR。
5. 用玩家网络确认每个 JAR URL 返回原始文件而不是 HTML。
6. 最后上传新的 `mods.txt`。
7. 用全新电脑端、旧电脑端、目标手机启动器分别测试。
8. 检查日志中的清单版本和双哈希结果后再通知玩家。

不要先发布清单再慢慢上传文件。CDN 存在缓存时，应确保清单和文件不会跨版本混用。

## 9. 正常退出语义

必须条件不满足时会输出 `STARTUP_BLOCKED`，显示错误信息，然后以退出码 `0` 终止当前游戏进程。这样启动器应显示“正常退出”，但 Minecraft 主类不会运行。

同样，Windows/Fabric 文件占用导致需要退出后更新，或者手机端更新后需要重新启动时，也使用正常退出。是否真正阻止进入游戏应以日志和 Minecraft 主类是否启动为准，不能仅根据退出码判断同步成功。

## 10. 日志诊断

排错时收集：

- `logs/latest.log`；
- `.modsync/helper.log`；
- `.modsync/ui-status.txt`；
- `.modsync/progress.log`；
- `.modsync/recommended-selection.properties` 中不含敏感 URL 的部分；
- 浏览器直接访问 `mods.txt` 的结果。

对外发送日志前，应去除账号、签名 URL、内部域名和本机路径。
